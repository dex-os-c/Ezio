## Tor Browser stream-isolation compatibility

**Status:** DONE — live-verified 2026-07-30.

Tor Browser 15.0.19 (bundled Tor 0.4.9.11) was run as a real local bundle.
Ezio detection returned `source="tor_browser"` for
`127.0.0.1:9150`. With credentials generated by
`scraper.tor_socks_credentials()`, Tor ControlPort `STREAM` events showed:

- `www.iana.org` → circuit 46;
- `www.rfc-editor.org` → circuit 44;
- repeat `www.iana.org` with the same credential → circuit 46.

The two distinct host/credential pairs therefore isolated, and same-host
reuse held. The proof used live ControlPort events, not inferred behavior.
Tor Browser's ControlPort was loopback-only at `127.0.0.1:9151`; unauthenticated
access was rejected and the default `control_auth_cookie` authenticated
successfully. This confirms reachability/authentication for the deferred
rotation item only; no rotation behavior is implemented here.

## Pacing for the enrichment / reputation API clients

**Status:** Class B **DONE 2026-07-29** (16 sites). Brief 2.4 additionally
landed the GreyNoise safety cap, crt.sh and ransomware.live pacing, NVD
rolling-window tracking, the `VT_API_TIER` flag, and `Retry-After` handling.

**Still open:** Class A (plain request timeouts) — never in scope for these
briefs. And pattern 1 (the persistent budget/counter store) plus the proactive
half of pattern 3, both scoped at the foot of this section and deliberately not
committed to.

Phase 1a introduced `pacing/` (`quiet` / `normal` / `aggressive`) and routed
every scraper-side timeout, retry count, retry backoff, and politeness delay
through it. The enrichment/reputation API clients under `sources/` were left
outside that scope, because some of their delays encode a provider's published
quota and a naive `aggressive` multiplier that shortens those risks a 429 —
a worse outcome than being slow.

A full provider-by-provider audit against each vendor's **live documentation**
on **2026-07-29** replaced the original guesses. The findings below are that
audit, not the pre-audit estimate; three items were confirmed bugs in shipped
code.

### The floor rule — `scale_delay_floor()`

Class B must not reuse `pacing.scale_delay()`, which is symmetric and scales
`aggressive` downward at 0.25×. It uses a dedicated helper whose defining
property is that it can only ever return a value ≥ the baseline it is given:

```
scale_delay_floor(documented_delay) >= documented_delay   # for EVERY profile
```

`quiet` scales the documented delay upward (exceeding a rate-limit interval can
never trigger a 429); `normal` returns it unchanged; `aggressive` **clamps at
the documented delay as a hard floor**. `aggressive` therefore buys nothing on
Class B sites, and that is the intended outcome.

The point of the asymmetry is that it makes the quota guarantee **structural
rather than procedural**. A reviewer only has to confirm the helper is monotonic
non-decreasing, instead of re-verifying every provider's published limit each
time the scale factors are tuned.

### The concurrency rule — `rate_limit_delay(min_interval, concurrency)`

A bounding semaphore and a per-request delay are two independent mechanisms that
**multiply**: N workers each sleeping the documented interval produce N times the
documented rate. Both claim to represent the same real-world quota, so they are
derived from it together. The caller must sleep *inside* its semaphore — the slot
has to stay held for the delay or the arithmetic does not apply.

### The failure-path rule

The delay goes in a `finally` **inside** the semaphore. Returning early on a
non-200 skips it, which means a run of 429s — precisely what a rate limiter
emits — makes Ezio speed up instead of backing off.

Sites 15 and 16 were added by brief 2.4. Both were previously **unpaced
entirely**, and both needed more than a flat constant:

- **crt.sh** cannot cover MAX_DOMAINS (30) inside an investigation at 5 req/min
  (30 x 12.5 s = 6 min), so `CRT_SOFT_BUDGET` (45 s) bounds it the way
  `nvd.py`'s budget bounds its CVE loop. That is a real coverage reduction and
  the correct trade — 30 concurrent requests at a 5/min endpoint got throttled,
  so most of them were returning nothing anyway. The 24 h in-memory cache and
  the cross-process enrichment cache are what recover coverage across runs.
- **ransomware.live** is limited per *endpoint*, so `/groups`, `/group/{name}`,
  `/v2/recentvictims` and `/v2/recentcyberattacks` each hold their own
  allowance. One flat delay would be either wrong (global, needlessly
  serialising unrelated routes) or unsafe (per-call, missing that five
  concurrent `/group/{name}` calls share one route). Hence `_rl_route_gate()`,
  which keys a last-request timestamp by collapsed route, and
  `_RL_MAX_GROUP_DETAILS` (2, was 5) with a soft budget. Only the *detail*
  fetch is capped — every matched group still contributes its summary record.

Supporting constants, same mechanism: `github_scraper.BLOB_FETCH_RATE_LIMIT_DELAY`
and `gitlab_scraper.PROJECT_RATE_LIMIT_DELAY` (1.0 s each) replaced an arbitrary
hardcoded `delay / 2` divisor. These hit the core REST API (GitHub 5,000/hr auth,
GitLab `/projects/:id` 400/min), not the search quota.

#### What the audit corrected

- **`aggressive` was violating three providers' documented limits in shipped
  code.** `github_scraper.py`, `gitlab_scraper.py` and `paste_scraper.py` used
  the symmetric `scale_delay()`. Measured: GitHub code search 6.5 s → 1.625 s
  under `aggressive` against a documented 6.0 s floor.
- **LeakCheck was unsafe even at `normal`** — 0.4 s against a documented 1 RPS,
  2.5× over the limit. Corrected to 1.1 s.
- **Three clients paced at zero on failure.** XposedOrNot, LeakCheck and Hudson
  Rock returned before their `sleep()` on any non-200. Measured pre-fix: 12
  sequential 429s left with a mean gap of **0.0000 s**.
- **GitLab breaks the "authenticated == faster" pattern.** Its `/search` cap is
  per-IP and a token does not lift it. The old 4.0 s / 1.0 s AUTH/UNAUTH split
  was over the real 10 req/min in *both* branches; the split is now gone, and a
  test asserts the constants stay gone.
- **The semaphore and the delay were multiplying.** Concurrency 2 with a 0.5 s
  sleep gave ~4 req/s against XposedOrNot's documented 2 req/s.
- **The inventory was 14 sites, not 9** — Shodan, both git-forge scrapers and
  the paste sources were missing from the original list.

### DONE 2026-07-29 (brief 2.4) — quota guard, rolling window, tier flag, headers

**GreyNoise safety cap** — `MAX_GREYNOISE_LOOKUPS = 12`, enforced by
`GreyNoiseBudget` in `ip_reputation.py`. The free tier is **50 lookups/week**
(10/day unauthenticated, shared with the Visualizer) and `MAX_IPS` is 50, so one
investigation could exhaust a week's access; measured before/after, 50 outbound
lookups became 12. Deliberately a *safety cap*, not a budget tracker: it bounds
one run, keeps no cross-run state, and sits low enough that four investigations
share a week without any tracking. Cache hits do not consume budget (they issue
no request). The cap surfaces in `sources_used` as `_greynoise_capped_at_N`
rather than silently thinning coverage.

**NVD rolling window** — `pacing.RollingWindow` (a deque of request timestamps)
replaced the flat inter-request delay. A flat delay enforces the correct *mean*
rate but has no memory of when earlier requests went out, so a burst-then-idle
pattern can still exceed the limit inside some 30 s span. Measured: with a
scaled 5-per-1 s model, the flat delay put 6 requests inside 0.510 s (violation);
the window's tightest 6-request span was 1.006 s. The window enforces the
documented spacing too, via `acquire(min_spacing=...)`, so NIST's "sleep six
seconds between requests" and the 5-per-30 s cap are one mechanism rather than
two that would double-count. In-process state only, kept NVD-local — NVD is the
only provider in the tree documenting a rolling window, and a shared abstraction
with one consumer is the dead-generality problem `pacing/` exists to remove.

**`VT_API_TIER`** — `public` (the default, and the fallback for any unrecognised
value, since guessing premium wrongly earns a 429) keeps the documented 15 s
floor. `premium` / `paid` / `enterprise` get a 0.25 s courtesy gap instead: a
20-hash investigation drops from 300 s to 5 s. This is the **only** enrichment
delay that uses the symmetric `scale_delay()`, and correctly so — premium has no
published limit, so there is no quota to protect and `aggressive` may genuinely
shorten it. A test pins that the exception lives in `_vt_delay` and nowhere else.

**`Retry-After` / `X-RateLimit-Reset`** — `pacing.retry_after_seconds()` handles
delta-seconds, HTTP-date, epoch-ms and epoch-second forms, ignores stale or
clock-skewed values, and clamps at `MAX_SERVER_DECLARED_WAIT` (120 s) so a
provider answering "come back in an hour" degrades that source instead of
blocking the pipeline. Wired into the 429 branches of XposedOrNot, LeakCheck,
Hudson Rock, NVD, VirusTotal and crt.sh. `_parse_rate_limit_reset` in
`api/routes/investigations.py` now delegates to it, so there is one
implementation shared with the LLM retry path rather than two that can drift.

One design distinction worth keeping: the helper separates `fallback` (used only
when no header is present) from `floor` (the minimum in all cases). For an
enrichment client both are the documented interval — a server saying "1 second"
does not license undercutting a documented 15 s, since both constraints bind.
For the LLM path, 65 s is a *guess* ("outlast a 1-minute window") rather than a
quota, so it passes `floor=5.0` and a server asking for less is honoured.

### Deferred — the rate-limit shapes still unaddressed

Scoping only. Neither is required for 2.0.0.

**Pattern 1 — non-time-bound caps. STILL OPEN.** VirusTotal 500/day,
XposedOrNot 25/hr + 100/day, BlockCypher 100/hr, AbuseIPDB 1,000/day, GreyNoise
50/week, EmailRep 250/month, GitHub 60/hr unauthenticated, MalwareBazaar 2,000
downloads/day. These need a counter that persists across requests within the
window — a per-request delay cannot express them at all, and
`MAX_*_PER_INVESTIGATION` caps bound a single run, not a day.

The GreyNoise cap above is explicitly *not* this: it is a per-run safety bound
that needs no persistence. A real budget tracker needs three decisions that are
product decisions, not implementation details:

1. Where the counter persists. `utils/enrichment_cache.py` is a value cache, not
   a counter, so this is a new store.
2. Whether the budget is per-process, per-machine or per-deployment. GreyNoise's
   50/week is per *account*, so a key shared across machines needs shared state.
3. What the user sees when a provider is exhausted mid-investigation.

**Pattern 2 — rolling windows. DONE for NVD** (above). No other provider in the
tree documents one; if one appears, `pacing.RollingWindow` is reusable as-is.

**Pattern 3 — server-declared limits. Reactive half DONE, proactive half open.**
Honouring a 429's own headers is done. What remains is *proactive* quota
modelling for urlscan.io and Hybrid Analysis, which publish no numbers by design
and expose remaining quota only through response headers on successful requests.
That means tracking headroom across requests, which is pattern 1's store — worth
building only on top of it, not before.

**Pattern 4 — key tiers that don't behave. DONE.** GitLab `/search` is per-IP
regardless of token (handled, with a test asserting the AUTH/UNAUTH split stays
deleted); VirusTotal now has `VT_API_TIER`. The durable lesson is recorded in
`sources/nvd.py:_request_delay` — NVD is the pattern, GitLab the
counter-example, and each provider must be checked rather than assumed.

**Remaining unpaced providers with real documented limits.** crt.sh and

Still unpaced:

## Stylometry authorship-pair calibration dataset

**Priority:** Low / non-urgent  
**Status:** Future task — calibration remains intentionally gated off until this is complete.

Source or construct a labeled authorship-pair dataset for the stylometry evaluator. The dataset must contain both:

- same-author text pairs; and
- different-author text pairs.

The data should document provenance, licensing/usage permissions, language, minimum text lengths, author and pair counts, and any train/validation/test split. Avoid leakage between splits (for example, pairs from the same author should not cross evaluation boundaries in a way that inflates performance).

### Acceptance criteria

1. A reproducible, documented dataset is available to the project or can be generated from published data.
2. The dataset is formatted for `scripts/evaluate_stylometry.py` (`text_a`, `text_b`, `same_author`).
3. Evaluation produces a committed calibration artifact containing the selected threshold, validation-pair count, false-match rate, true-match rate, true-negative rate, and reference statistics.
4. The artifact is configured through `STYLOMETRY_CALIBRATION_FILE` only after review of its provenance and evaluation design.
5. Until these criteria are met, stylometric results must continue to be reported as uncalibrated and must not produce same-author match decisions.
